# GH200 bring-up, measurement and stop conditions

**Release status: host-tested arithmetic, uncompiled CUDA prototypes, no GPU measurements.** This is a research kernel plus harness, not an installed pretrained-model accelerator.

## 1. CPU and formal checks first

From the repository root:

```bash
python -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements-test.txt
python -m pip install -e .
pytest -q
python scripts/run_v2_experiments.py
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --parallel
python scripts/check_host_intervals.py
python scripts/check_host_residuals.py
bash scripts/check_lean.sh
```

The Lean command requires an installed Lean/elan environment and network access for the pinned mathlib revision. It exits nonzero if Lake is unavailable. A supplied CI workflow is not a successful build record. First obtain a clean pinned build, review every printed theorem dependency, and retain the complete log. No proof-status flag may be set true from a text scan alone.

## 2. Compile the SM90 local gate

Use the CUDA and PyTorch installation appropriate to the actual GH200 image, including its CPU architecture. Do not replace that installation with an arbitrary desktop wheel. Record the driver, CUDA compiler, host compiler, Torch version, GPU capability, HBM capacity/type, clocks and power limits. NVIDIA's Grace tuning guide is the topology/placement reference [R6].

```bash
nvidia-smi
nvcc --version
cmake -S . -B build-gh200 -DSTATECUT_CUDA=ON -DCMAKE_BUILD_TYPE=Release
cmake --build build-gh200 --parallel
./build-gh200/statecut_cuda_smoke
python scripts/bench_gh200.py \
  --library build-gh200/libstatecut_residual_cuda.so \
  --length 32768 --heads 8 --dim 64 --repeats 100 \
  --out results/gh200_microbenchmark.json
```

`statecut_cuda_smoke` is the inherited **real-softmax** synthetic test, not an E24/pretrained equivalence test. `libstatecut_residual_cuda.so` implements the new **E24 residual gate**. Keep their numerical contracts distinct.

The new gate takes `q[H,D]`, per-head frontier key boxes, counts, value extrema, outward first-moment intervals and proposed BF16 bits. It has **no raw K/V pointer**. Each CTA computes one node's residual bounds at the proposed cells; a second kernel sums a head's frontier and requires all coordinates plus positive denominator. The supported key/value dimensions are independently 1 through 128. Counts are positive signed-int-compatible values, not zero-padded inactive nodes. Finite/outward metadata must describe exactly the intended visible rows. Scores outside the supported exponential enclosure domain `[-64,64]` fail closed.

`CudaFrontier` retains allocations, launches on the specified tensor device/current stream and returns per-head flags. It does not provide generation-safe serving ownership, graph-safe external lifetimes, a GPU forest builder or a fallback scheduler. Per-head flags are not a full token/state certificate.

## 3. Read the microbenchmark correctly

The synthetic keys and values are nonconstant. Its proposed output is known from the construction, not computed by a hidden dense oracle. Summary construction does scan raw tensors once and its time is recorded separately. The script records device-event timings and synchronized wall timings for the gate and for Torch SDPA. The two paths have different numerical contracts, so the script deliberately does **not** report their ratio as a certified speedup. The observed BF16 comparison is a diagnostic only.

Run `compute-sanitizer --tool memcheck` and `--tool racecheck` on a short microbenchmark before collecting results. Device testing must be extended beyond the construction to boundary-adjacent, mixed-sign, underflow, overflow, invalid-metadata, odd-significand and partial-frontier cases, cross-checked against the rational oracle. The exhaustive host-cell checks do not validate device instructions. All device validation is outstanding in the supplied release.

## 4. Probe a pretrained checkpoint without changing its answers

The optional scripts require Torch, NumPy and Transformers. They are written against the current documented attention interface [R11], but no Transformers checkpoint run was possible here. Prefer an isolated evaluation environment and record its exact package versions. No checkpoint weights are bundled.

```bash
# Use an existing local BF16-capable checkpoint and a nonempty prompt file.
python scripts/capture_pretrained.py \
  --model /path/to/local/checkpoint \
  --prompt-file /path/to/prompt.txt \
  --output results/checkpoint-capture --steps 3 --limit 4 --max-rows 4096

python scripts/audit_capture.py \
  results/checkpoint-capture/capture-0000.npz \
  --heads 1 --block-size 128 --max-expansions 0 \
  --output results/checkpoint-e24-observation.json
```

A hub identifier additionally requires `--revision` with its immutable 40-hex commit. The capture script disables remote custom model code. It records model/artifact hashes, prompt hash, observed token IDs, package/device versions and capture coverage. It records Q/K/V *as actually passed to SDPA*, so an upstream RoPE transform is not invented by the observer. GQA mapping is recorded when the supported call exposes it.

Only batch-one, single-query, finite BF16, zero-dropout, fully visible zero-bias attention is captured. Nontrivial masks, causal-call semantics and overlong caches are skipped with explicit reasons, never dropped or truncated to manufacture coverage. Zero captures is a failed probe, not success. Calls through different imported aliases or fused paths can bypass the observer, so coverage must be inspected. The process must be isolated and single-threaded because the wrapper temporarily changes a Python module function.

The returned SDPA output is unchanged. Capturing synchronizes, copies full selected caches to CPU and writes files. Its latency is unusable for performance claims. The offline audit evaluates E24 and compares observed output bits, including any signed-zero mismatch. Even perfect observed matches set `backend_replacement_authorized` to false because the deployed numerical bridge is missing.

## 5. Required production work and faithful fallback

A production path still needs a sound incremental GPU summary builder, immutable/versioned frontier ownership, refinement and exact dense fallback, and graph integration for complete write-frontier certification. Masks, bias, RoPE, GQA/MQA sharing, per-layer positions and current-token append semantics must match the chosen backend. Sharing raw KV and metadata across query heads must not multiply persistent writes.

Stage all proposed writes privately, publish only after validation, and make fallback start from the unchanged committed state. Do not replay a failed token on a cache that already contains its speculative append. Memory addresses and shapes do not establish sequence identity; use owner, generation, branch, layer, position and numeric-profile identity. Never call a full-cache audit or hash on the measured per-token path. Validate provenance at creation or version changes.

The rational fallback can reuse opened contributions because its sums are exact. A pinned floating implementation cannot reuse arbitrary reassociated contributions without proof. It may need to reread the entire cache after failed exploration. Charge those reads.

Keep raw historical KV in HBM for the first end-to-end comparison. Grace-memory offload is a separate experiment with explicit NUMA placement, migration, C2C traffic and prefetch accounting. Do not use a dual-superchip aggregate specification as a single-device or one-direction bandwidth number.

## 6. Measurement matrix and acceptance criteria

Compare the pinned dense backend, always-fallback filter, independent-ratio filter, centered-quotient filter, direct-residual filter and write-frontier execution. Use identical checkpoint, prompts, greedy policy, mask, precision, batch, context and serving settings. Test realistic prompts plus random tokens, repeated tokens, needle queries, boundary-adjacent outputs and near-tied logits. Count full state equality, not just perplexity or next-token agreement.

Record prefill/index-build time, persistent metadata bytes, tail/carry maintenance, proposal cost, root/child summaries visited, raw rows and raw bytes read, fallback fraction, accepted writes, time to first token, p50/p95 decode latency, tokens/s, HBM/C2C traffic, and any synchronization. Include all layers, MLP/weight work, output head, batching, rejected attempts and GPU launches. Report warm and cold/long-history behavior separately. Use held-out prompts and freeze thresholds before final evaluation.

For `m` full leaves, a compact full forest has fewer than `2m` nodes. A proposed descriptor with two FP64 key-bound vectors, two value extrema, a two-endpoint first moment and a count uses `8(2d_k+4d_v)+4` bytes before alignment/pointers. Relative to BF16 raw KV, the metadata ratio is approximately

```
[8(2*d_k+4*d_v)+4] / [B*(d_k+d_v)]
```

when the nearly `2N/B` nodes are all stored. At equal dimensions the leading term is `24/B`, before headers, tails and versioning. This is a derived layout estimate, not the footprint of Python Fraction objects. Compression of summaries requires sound outward rounding and its own cost accounting.

A paper-level acceleration claim requires `filter + extra maintenance < accepted_fraction * dense_work_saved` in a measured same-contract system. Reject that claim on any state mismatch, unsupported backend path, empirical-only error bridge, missing launch/maintenance cost, or loss against the unchanged dense baseline. A zero-raw-read local gate can still be slower end to end.
